# Проверка CRM перед демонстрацией заказчику

Дата: 25.09.2026. Основание: приложенное «ТЕХНИЧЕСКОЕ ЗАДАНИЕ (1).docx», исходный код, работающий локальный стенд и дополнительные проверки.

Основные модули ТЗ представлены, интерфейс выглядит цельным. Перед демонстрацией приоритетнее исправить цепочку документов, согласованность аналитики и поведение при ошибках. Расширение функциональности можно отложить до этих исправлений.

Это результат проверки, а не акт полной приёмки. Исправления по пунктам ниже внесены после проверки и покрыты тестами `backend/tests/test_demo_regressions.py`.

## Что проверено

- `npm run build`: успешно, включая проверку TypeScript.
- Существующие интеграционные тесты: **33 passed**, одно предупреждение об устаревающем API зависимости.
- Тесты выполнялись с текущим кодом в отдельной БД `crm_audit_20260925` и Redis DB 14. Дополнительные операции создания документов тоже выполнялись только в этой БД.
- На работающем стенде проверены ответы API компаний, лидов, канбана, задач, КП, счетов и отчёта по менеджерам: HTTP 200.
- В браузере Edge проверены дашборд, канбан, календарь и отчёты на ширинах **1920, 1366, 768 px**. Общего горизонтального переполнения страницы и ошибок JavaScript в этом прогоне не обнаружено. Это не полная проверка всех форм и доступности.
- Ошибки HTTP 500 имитировались перехватом запросов в тестовом браузере, без остановки сервера.
- Проверка потери правок КП выполнялась без сохранения: запросов изменения КП на сервер не было.
- Нагрузочный тест, восстановление из резервной копии и реальные интеграции заказчика в этом аудите не запускались.

## Исправить перед показом

### 1. Валюта и НДС теряются при выставлении счёта по КП — высокий приоритет

**Воспроизведено:** сохранённое КП на **100 USD, без НДС** превращается в счёт на **100 RUB, НДС 20%** при запросе, который отправляет интерфейс.

Кнопка передаёт только идентификаторы КП, сделки и компании. Backend берёт валюту и НДС из значений по умолчанию запроса, а не из исходного документа.

Источники: [ProposalEditor.tsx](../frontend/src/pages/proposals/ProposalEditor.tsx), функция `invoice`; [schemas/documents.py](../backend/app/schemas/documents.py), `InvoiceCreate`; [api/v1/finance.py](../backend/app/api/v1/finance.py), `create_invoice`.

**Доработка:** наследовать валюту и НДС исходного КП на сервере, если пользователь явно не задал другие значения; аналогично проверить счёт из сделки. После создания открывать конкретный счёт, а не общий список.

**Критерий готовности:** валюта, ставка НДС, позиции и итог совпадают в КП, счёте и его PDF. Проверить варианты RUB/USD/EUR и доступные в приложении ставки НДС.

### 2. Сводка финансов складывает разные валюты — высокий приоритет

**Воспроизведено:** добавление счёта на **100 USD** увеличивает общую дебиторскую задолженность ровно на **100**, хотя интерфейс показывает сводку в рублях. В расчёте сумм нет пересчёта по курсу; та же проблема видна в коде подсчёта поступлений.

Источники: [api/v1/finance.py](../backend/app/api/v1/finance.py), `invoices_summary`; [FinancePage.tsx](../frontend/src/pages/finance/FinancePage.tsx), карточки показателей.

**Доработка:** использовать единый механизм пересчёта валют с аналитикой либо показывать отдельные итоги по валютам. Отображать, какой курс используется.

**Критерий готовности:** сумма долгов и оплат нескольких валют совпадает с расчётом по выбранным курсам и согласуется с отчётами.

### 3. Ошибка загрузки выглядит как отсутствие данных — высокий приоритет

**Воспроизведено в браузере при HTTP 500:**

- Дашборд продолжает показывать восемь заглушек загрузки после завершения повторного запроса.
- Компании показывают «Компании не найдены».
- Задачи показывают «Задач нет».

Это может создать у заказчика впечатление потери данных или зависания системы.

Источники: [DashboardPage.tsx](../frontend/src/pages/DashboardPage.tsx), [CompaniesPage.tsx](../frontend/src/pages/companies/CompaniesPage.tsx), [TasksPage.tsx](../frontend/src/pages/tasks/TasksPage.tsx). Эти экраны используют `data` и `isLoading`, но не выделяют состояние `isError`.

**Доработка:** явные состояния «Загрузка», «Данных нет», «Не удалось загрузить», кнопка «Повторить». При сбое обновления сохранять уже загруженные данные с отметкой об ошибке.

**Критерий готовности:** HTTP 500 и обрыв связи не дают ложного пустого состояния; после восстановления связи экран можно обновить без перезахода.

### 4. Период дашборда не управляет графиком выручки — средний приоритет

**Воспроизведено через API:** для сентября 2026 сводная выручка — **5 975 400 ₽**, для января — **7 602 440 ₽**, но массив `revenue_by_month` в обоих ответах одинаков. В текущем ответе **13 месяцев**, хотя функция запрашивает 12.

Причины: в `revenue_by_month` не передаётся выбранный период; начало интервала вычисляется вычитанием `31 * (months - 1)` дней вместо календарных месяцев.

Источники: [api/v1/analytics.py](../backend/app/api/v1/analytics.py), `dashboard`; [services/analytics.py](../backend/app/services/analytics.py), `revenue_by_month`.

**Доработка:** график должен учитывать выбранные даты, либо иметь явно подписанный независимый период. Для воронки и прогноза также ясно обозначить временные границы: текущий срез и будущие месяцы соответственно.

**Критерий готовности:** выбор месяца, года и произвольного интервала даёт объяснимые, согласованные цифры; интервал «12 месяцев» содержит ровно 12 календарных месяцев.

### 5. Несохранённые правки КП теряются — средний приоритет

**Воспроизведено в браузере:** изменить заголовок черновика → перейти в «Компании» через меню → вернуться в КП. Изменение потеряно, предупреждения нет.

Дополнительно по коду: действие «PDF» сохраняет изменения перед формированием, но «Скачать PDF» из меню и «Выставить счёт по КП» не выполняют такую проверку. Они могут использовать предыдущую сохранённую версию, пока пользователь видит новые значения в редакторе.

Источник: [ProposalEditor.tsx](../frontend/src/pages/proposals/ProposalEditor.tsx), `dirty`, `preview`, `invoice` и обработчик «Скачать PDF».

**Доработка:** предупреждение при уходе со страницы и единый порядок сохранения перед скачиванием, копированием и созданием счёта. После неудачного сохранения зависимое действие не выполнять.

**Критерий готовности:** PDF и счёт соответствуют видимому содержимому редактора; переход в другой раздел требует выбора «Сохранить / Уйти без сохранения / Остаться».

## Что улучшит впечатление от демонстрации

1. **Короткий сквозной сценарий на 10–15 минут.** В проекте уже есть [сценарий на 30–40 минут](demo-script.md). Для первого показа подготовить сокращённый: входящий лид → компания/контакт/сделка → товары и задача → КП и согласование → счёт и частичная оплата → показатели руководителя. Использовать одного клиента, чтобы связь шагов была очевидна.
2. **Фирменное оформление заказчика.** Использовать существующие настройки названия, логотипа, реквизитов и цвета шаблона. Подготовить один аккуратный PDF КП и счёт с реалистичными товарами и контактами. Переработка всего интерфейса для этого не нужна.
3. **Переходы от показателей к действиям.** Сделать кликабельными «Просроченные задачи», «В работе», «Дебиторская задолженность» с открытием соответствующего отфильтрованного списка. Сейчас карточки показателей в основном информационные.
4. **Сохранение контекста списков.** Сохранять поиск, фильтры, сортировку, страницу и вид канбана/списка в URL или настройках. Возврат из карточки должен возвращать пользователя к прежней выборке.
5. **Ясные статусы интеграций.** На показе отделять подключённые сервисы от демонстрационных. Например, mock-телефония создаёт событие без реального звонка, а общая кнопка сообщает «АТС соединяет вас…». Сообщение должно учитывать режим провайдера.
6. **Завершённый раздел помощи.** Сейчас «Видеоуроки» — текстовые названия с длительностями, без видео. Для показа подойдут 2–3 реальные короткие записи либо явный блок «План обучения» без имитации проигрывателя.

## Что уточнить в документах о готовности по ТЗ

- Проверка на **1560 компаниях** в `load-test.md` не доказывает выполнение требования раздела 4.1 о списках до **10 000 записей**. Это отдельный будущий прогон; существующие результаты не нужно выдавать за него.
- Наличие сценария восстановления и быстрое восстановление демо-БД не подтверждают время восстановления системы с реальным объёмом вложений. Автоматический сервис резервного копирования сохраняет PostgreSQL; копирование S3 вынесено в ручные инструкции по развёртыванию. Перед вводом в эксплуатацию нужны автоматизация и контроль восстановления файлов вместе с БД.
- Реальные SIP-АТС, IMAP/SMTP, Telegram, загрузка XML в конкретную конфигурацию 1С требуют проверки с сервисами заказчика. XML-экспорт сам по себе не является подтверждением готовой двусторонней интеграции с 1С.
- `test_reports` проверяет ответы, наличие колонок, отдельные свойства воронки и ограничения доступа. Полную сверку сумм отчётов с независимым расчётом эти тесты не делают, что подтверждается найденными расхождениями.
- Текущий документ `tz-compliance.md` стоит дополнить статусом «Реализовано, требует проверки» для пунктов, по которым пока есть только код или архитектурное описание. В частности, потенциальное масштабирование до 500 пользователей не равно подтверждённой нагрузочной проверке.

## Рекомендуемый порядок работ

1. Исправить наследование валюты/НДС и расчёт финансовых сводок.
2. Добавить понятные ошибки загрузки и защиту несохранённых КП.
3. Согласовать периоды графиков и показатели отчётов.
4. Подготовить короткий сценарий, фирменные документы и ясные статусы интеграций.
5. Провести репетицию полного пути по исправленной версии, затем отдельную приёмку нагрузки, восстановления и интеграций.
